1. Stack

  • CMS: Sanity Studio (schema-driven, singleton + collection documents)
  • Frontend: Next.js (App Router), React, Tailwind CSS, Framer Motion
  • Hosting: Vercel
  • Content fetch: fetchContent(query, params) → wraps sanityClient.fetch, draft-mode aware, 10s revalidate on published content. Not used inside generateStaticParams — see §5.

3. Content Model

Global / shared singletons

siteSettings

Stats array (value/label — the "By the numbers" block, shared by Home and Who We Are so the figures never drift out of sync), statsImage, socialLinks (Facebook, LinkedIn), footerTagline, and globalCta new — the site-wide bottom-of-page CTA (sectionLabel, headingLine1/headingLine2, ctaLabel, background image). Queried independently by any page that needs it, and by the Footer for the tagline/social links.

seoSettings pre-existing, unchanged

Site-wide SEO defaults plus siteName, phone, email, address. Contact page's "Our office" block reads its address/phone/email from here rather than duplicating them — single source of truth.

navigation modified

Extended with an optional children array per nav link to support the Services dropdown — the base template's flat link list didn't support this.

contactForm pre-existing, unchanged

Form submission storage — name, email, phone, message, timestamp.

Collections

caseStudy new

10 documents (Irish Hospital Apartments is the flagship, plus Elkhorn, Fremont/Colorado Springs, West Bend, Marshfield, Pulaski, Watertown, Langlade County, Asset Mapping, Phelps WI). Fields: title, slug, location, heroImage, quickFacts[] (variable count, icon+text), story[] (one or more sections, each with its own heading and up to 3 text blocks — supports multi-part narratives), optional testimonial reference, relatedServices[] (up to 3 references into the five service-page singletons).

testimonial new — replaces base testimonials

One pool of ~14 quotes, deployed two ways from the same documents: featured (boolean) picks the 3 shown in the homepage/Contact/Our-Projects carousel; linkedCaseStudy (optional reference) is set for the ~9 that are a specific case study's pull-quote, and left empty for the ~5 shown only as modal cards on the Our Projects grid.

workExample new

~48 lightweight project write-ups (10 Analysis / 12 Strategy / 6 Redevelopment / 11 Financing / 9 Implementation — matches the homepage's "48 projects on record" stat), each tagged with a category matching a service page. Each service page queries only its own category. Optional linkedCaseStudy reference drives the "Learn about the X project" button — present only when a full case study page exists for that example.

Page singletons

Every page schema groups its sections as numbered object fields (①②③…) plus a final SEO group — the frontend passes each group whole to its corresponding component. See the schema files themselves for exact field lists; summarized here is what each page is built from and its one or two non-obvious decisions.

  • homePage — hero, approach, a fixed 6-card services grid (5 services + a "not sure where to start" CTA card, each independently editable — not pulled live from the service pages), a public/private-sector teaser, and a testimonialSection new group (sectionLabel + heading only — the quotes themselves are the top-level testimonial collection query, not stored on the page). Named testimonialSection rather than testimonials specifically to avoid confusion with the testimonial collection type — keep that naming distinction if this pattern is copied to Contact or Our Projects.
  • whoWeServePage — public/private sector sections, each with two subsections (Municipalities/Organizations, Entrepreneurs/Private Developers) whose CTA is a reference to a case study, not a hardcoded URL — the destination project can change without a schema edit.
  • analysisPage / strategyPage / redevelopmentPage / financingPage / implementationPage — identical shape: hero, overview, a variable-count offerings array (2–6 cards depending on the service), and a heading/intro for the workExample list pulled by category.
  • ourProjectsPage — hero, overview, and a flagship-project block that references the Irish Hospital Apartments case study specifically.
  • whoWeArePage — hero, story (body is now a 2-paragraph array updated, following the standing paragraph-array convention rather than a single blob), a new purpose group new ("Our Purpose" — sectionLabel, heading, body, a fixed-destination cta to /contact, and a values array of 4 core-value cards, each {heading, body}), stats section (image only — the numbers come from siteSettings), and two independently editable arrays: leadership team and interns, both add/edit/remove rather than fixed-count. The original Company Summary section is removed removed (commented out in the schema, not deleted outright — restore it there if it needs to come back).
  • contactPage — hero only. No CMS fields for office info (pulled from seoSettings) or the form itself (a submission handler, not CMS content).

4. Query Architecture

Three shapes are in use, all following the generator's SCREAMING_SNAKE_CASE naming with the export name matching the filename exactly:

  1. Plain singleton — *[_type == "x" && _id == "x"][0]{ ... }. Used where the page has nothing else to pull in (Who We Serve).
  2. Compound — { "page": *[...][0]{...}, "otherThing": *[...]{...} }. Used everywhere the page needs its own content plus a related collection (testimonials, work examples, case studies). FETCH_HOME_PAGE_QUERY is the fullest example — three roots: page (the homePage singleton, including testimonialSection's copy-only group), siteSettings (stats + globalCta), and testimonials (the top-level *[_type == "testimonial" && featured == true] array). This is why page components read data?.page?.title instead of data?.title — and why buildPageMetadata.js needed a patch, see §5.
  3. Parameterized — *[_type == "caseStudy" && slug.current == $slug][0]{...}, used only by the case study detail route, paired with a separate FETCH_CASE_STUDY_SLUGS_QUERY for generateStaticParams.

5. Known Integration Gotchas

These are properties of the shared Sanity/Next.js template this project (and every Latz Web Design project) is built on — not bugs in this content model. Documented here because they bit this build at least once each; the generator's own standing instructions carry the full detail and fix for each.

generateStaticParams + draftMode fix supplied, verify next deploy Production build failed with Error: draftMode was called outside a request scope at the case study route's generateStaticParams. Root cause: fetchContent always calls draftMode(), but generateStaticParams runs at build time, before any request exists, so draftMode() has nothing to read. Fix: generateStaticParams now calls the raw sanityClient.fetch(SLUGS_Q) directly (imported from utils/cms/sanityConnection), bypassing fetchContent entirely — the page component and generateMetadata are unaffected and keep using fetchContent as before. Corrected app/our-projects/[slug]/page.js was handed back to Jordan; mark this confirmed once the next deploy succeeds.
Section-label leading dash open, unresolved Every schema's sectionLabel field ships its initialValue with a leading em dash baked in (e.g. '— Contact', '— Testimonials', '— Core values'), but the shared SectionHeading component also hardcodes — {label} when rendering it — so anywhere both are in play the label will double up ("— — Contact") unless one side drops its dash. Surfaced while wiring up GlobalCTA; hasn't been checked against the sections that are already live. Needs a single decision (component owns the dash, or the CMS value does) applied consistently across every sectionLabel field and every place SectionHeading is used — not a per-section patch.
SectionHeading — optional second heading line components/ui/SectionHeading.js now accepts an optional headingLine2 prop, rendered on its own line under heading via a <br /> — added for GlobalCTA's two-line "Have a project in mind? / Tell us about it" heading, where the line break needs to hold regardless of how long the client's edited copy gets (so it's two explicit CMS fields, headingLine1/headingLine2, not a single field relying on width-based wrapping). Backward compatible — every other caller only passes heading and is unaffected.
buildPageMetadata.js patch confirmed applied The shared utils/seo/buildPageMetadata.js originally read pageData?.seo and called fetchContent(query) with no params — both broke under this project's own conventions: 9 of 11 pages use compound queries (so seo actually lives at pageData.page.seo), and the case study route needs $slug passed through. Unpatched, affected pages wouldn't error — they'd silently fall back to generic site-wide title/description. Now accepts an optional params argument (passed through to fetchContent(query, params)) and resolves seo as pageData?.seo ?? pageData?.page?.seo. Verified against the live file.
seoField.js Named export (import { seoField } from './partials/seoField'), not default — and it's ungrouped, so every schema spreads it as ...seoField.map((f) => ({ ...f, group: 'seo' })), exactly once.
structure.js / sanity.config.js sanity.config.js imports structure, singletonActions, and singletonNewDocument by those exact names — and the latter two must literally be the filter functions Sanity's document.actions/document.newDocumentOptions config expects, not data structures with similar-sounding purposes.
@sanity/icons Always import from a per-icon subpath (@sanity/icons/Cog), never a named block from the package root. Confirmed-safe icons for this install: Cog, Home, Users, BarChart, TrendUpward, Rocket, Folder, EarthGlobe, Envelope, Documents, Comment, Search, Link. Confirmed broken: Coins.
Section.js Every page wraps content in <Section> (components/layout/Section.js), not a bare <div>. Its py prop must be a full literal Tailwind class string ('py-8') — Tailwind can't see a class built at runtime (`py-${n}`).
Field/data naming — schema, query, and component must move together Renaming homePage.testimonials → testimonialSection (to stop it colliding with the testimonial collection type) broke the page silently because the query's nested field name, the top-level featured-quotes _type filter, and the destructured prop in app/page.js all needed the same rename and didn't get it — the featured-quotes query in particular was left filtering on the non-existent type testimonialSection, returning an empty array with no error. Worth flagging any time a field that's also queried elsewhere gets renamed: schema, query, and page-file destructuring are three separate places the name has to match.
